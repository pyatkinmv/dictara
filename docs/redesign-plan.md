# Редизайн Flutter-клиента — план и контекст

Рабочий документ ветки `redesign`. Цель — не потерять контекст между сессиями: что решили, что делаем, в каком порядке и что уже известно про окружение.

> **Этот документ относится только к редизайну интерфейса на моках** (итерации 0–10). Он остаётся как история этой работы и под интеграцию с бэкендом не обновляется. План интеграции с настоящим gateway (локальное окружение, срезы, защита прода) — в отдельном документе: [local-backend-integration.md](local-backend-integration.md).

## Цель

Привести Flutter-клиент (`app/`) в соответствие с HTML-дизайном `designs/1.9/cards-teal.html` — итеративно, по одному экрану за раз.

- Сначала **полный кликабельный макет на Flutter** с заглушками вместо данных (как моки в HTML). К gateway и серверу пока не ходим.
- Всё делаем **локально, в браузере**, прод не трогаем.
- Только Web, только широкий экран (макет рассчитан на сайдбар 220 px). Мобильную вёрстку и отдельное десктоп-приложение не делаем.
- Совпадение с дизайном — по вёрстке, цветам, отступам, состояниям и поведению, **не пиксель в пиксель**.
- Потом по экранам подключаем реальный API. Места, где нужны изменения на сервере, фиксируем по ходу (раздел «Изменения сервера» ниже и `docs/api-gaps.md`).

## Принятые решения

| Тема | Решение |
|------|---------|
| Ветка | `redesign`, от `master`. Вся работа только в ней |
| Защита прода | CI (`.github/workflows/ci.yml`) собирает образы и деплоит только на `push` в `master`; `pull_request` в `master` запускает только тесты. Пока работаем в ветке, прод не затрагивается |
| Где код | Правим тот же Flutter-код в `app/lib/`, отдельных папок под новый UI не заводим |
| Старый код | Новый UI показывается сразу; `TranscribePage`, `HistorySection` удаляем по мере замены. `ApiClient`, `AuthService` и текущие модели пока не трогаем — понадобятся при подключении сервера |
| Состояние | `provider` + `ChangeNotifier` (в проекте уже есть `AuthService extends ChangeNotifier`) |
| Навигация | `go_router`, у экранов свои адреса |
| Данные | Пока заглушки: интерфейс репозитория + `FakeRepository` с данными из HTML. Появится в итерации 2, когда нужны первые данные |
| Тема | teal; тема параметризуется, blue и violet — заменой токенов |
| Threads, Settings | Не в первой очереди, делаем в конце, если решим |
| Гранулярность | Итеративно, один коммит на итерацию, после каждой смотрим результат в браузере рядом с HTML |

- [ ] **12. Ревокация сессионных токенов** (найдено при проектировании авторизации для проигрывания аудио, итерация с плеером — см. ниже; само по себе в план редизайна не входило, но это дыра в безопасности, а не косметика)
  - **Проблема:** `JwtTokenProvider.issue()` (`gateway/.../service/JwtTokenProvider.kt`) выдаёт чистый stateless JWT (HMAC, без записи в БД) на `jwt.expiry-days: 30` (`application.yaml:35`) — 30 дней. Токен подписывает вообще все запросы к API (не только чтение — переименование, удаление, загрузка). У Flutter-клиента `AuthController.logout()` (`app/lib/state/auth_controller.dart:137`) чистит только локальный `_tokenStore` — на сервере токен как был валиден, так и остаётся до истечения `exp`. Нет ни одной таблицы/механизма отзыва (grep по `logout|revoke|blocklist|blacklist` в `gateway/src/main/kotlin` — пусто). Итог: если токен утёк (история браузера, скриншот, лог), у нашедшего полный доступ к аккаунту на срок до 30 дней, и «выйти» из аккаунта эту утечку не закрывает.
  - **Стандартный отраслевой подход (OAuth2-style):** короткоживущий access-токен (15 мин – 1 ч) для обычных запросов + долгоживущий refresh-токен (opaque random string, не JWT, хранится в БД: `user_id`, `expiry`, `revoked`), который умеет только одно — обменяться на новый access-токен через `/auth/refresh`. Logout = пометить refresh-токен `revoked`; максимум через час сессия мертва везде. Ротация refresh-токена при каждом использовании — повторное использование старого сигнализирует кражу. Плюс: настоящая ревокация. Минус: заметный объём работы — новая таблица/миграция, новый эндпоинт, во Flutter — перехват 401 → тихий refresh → повтор запроса.
  - **Более лёгкая альтернатива:** оставить один токен, но завести таблицу отозванных/активных сессий и проверять её на каждый запрос (дешёвый indexed lookup). Logout начинает реально работать, объём работы намного меньше access+refresh, из stateless JWT-философии выходим лишь частично.
  - Пока не сделано ничего; используется как есть. Учитывать при проектировании новых токенов (например, отдельный scoped-токен для проигрывания аудио по конкретному файлу — см. ниже — обходит проблему точечно, но не решает её в целом).

## Известные проблемы и несоответствия

- **Цвет тегов и спикеров.** `design.md` описывает поле `color`, назначаемое при создании по циклу из 10 цветов. `api-gaps.md` решает иначе: цвет считается на фронтенде по хэшу имени и API его не возвращает. Нужно выбрать одно.
- **Тип `Job.id`.** В `design.md` int, в БД UUID.
- **`app/pubspec.lock` был устаревшим.** В нём были лишние записи (`fluent_ui`, `intl` и др.), которых нет в `pubspec.yaml`. При добавлении `provider` и `go_router` (итерация 0) файл пересобран `flutter pub add`, лишнее ушло.
- **`dart:html`.** `AuthService`, `history_section.dart`, `transcribe_page.dart` используют устаревшую библиотеку; после итерации 1 они нигде не подключены (мёртвый код, удаляется по мере замены экранами). Пока такой файл импортирован, тесты работают только на браузерной платформе. В новом коде её не использовать; для скачивания и буфера обмена брать `package:web`.
- **CI не запускает Flutter-тесты.** В `ci.yml` нет `flutter test`.
- **`app/CLAUDE.md` устарел.** Он описывает старую структуру (`TranscribePage`, `HistorySection`) и решение «без state management»; обновить, когда старый UI будет полностью заменён.
- **Сессионные JWT нельзя отозвать.** 30 дней, logout только локальный. Детали и варианты решения — план, пункт 12.

## Как запускать приложение

Приложение ходит на относительный `/api/...`, который в проде проксирует nginx; на моках это не нужно. Для запуска с реальным gateway понадобятся Postgres + gateway (`docker compose up -d postgres gateway`) и прокси на `/api` (в gateway CORS не настроен). Без Telegram-токена gateway считает пользователя анонимным, так что интерфейс работает и без логина.

### Запуск нового UI на моках (проверено)

Точка входа проекта — `lib/material/main_material.dart` (не `lib/main.dart`), её нужно указывать явно:

```powershell
cd app
flutter run -d chrome -t lib/material/main_material.dart
```

В терминале, где запущен `flutter run`, доступны hot reload (`r`) и hot restart (`R`). Вариант `-d chrome` открывает браузер сам; **он на этой машине пока не проверялся**. Проверен вариант без запуска браузера: `flutter run -d web-server --web-port 3001 -t lib/material/main_material.dart`, затем открыть `http://localhost:3001` вручную (страница поднимается, CanvasKit отдаётся, в консоли ошибок нет; первая сборка ~40 с). Ошибка 404 на CanvasKit касается только тестового сервера `flutter test`, не `flutter run`.

`flutter run` при каждом запуске сам дописывает блок `analyzer.exclude` в `app/analysis_options.yaml`. Это побочный эффект инструмента, в коммиты его не берём (`git checkout -- app/analysis_options.yaml`).

- **Сайдбар прокручивается** при нехватке высоты окна (раньше был красный `BOTTOM OVERFLOWED` в debug и обрезка в release); тест на окно высотой 300 px.
- **Плашка статуса** получила минимальную высоту 18 px (Chrome округляет строку вверх), из-за чего шапка детали стала на 1 px ближе к макету.

#### Итерация 6: что важно знать

- **Поведение как в макете, включая спорное.**
  - Ряд «Speakers:» строится по **слотам** диаризатора и **не меняется** после выбора спикера в пикере: ручные назначения хранятся отдельно, по сегментам. После «All segments by X → Y» имена в транскрипте меняются, а чип в шапке остаётся прежним.
  - «This segment only» меняет только **первый сегмент блока**, хотя блок может состоять из нескольких.
  - «All segments by X» меняет все сегменты, которые сейчас приписаны спикеру с именем X (сравнение по имени).
- **Отклонения от макета:**
  - при создании спикер сохраняет регистр, введённый пользователем (макет берёт имя из поиска в нижнем регистре: `Create "alexei"`);
  - Enter в пикере выбирает или создаёт спикера (в макете обрабатывается только Escape).
- **Требования к серверу (api-gaps §1.3, §2.2, §2.5), решение по архитектуре по-прежнему не принято:**
  - нужна библиотека спикеров `GET/POST/PUT/DELETE /speakers`; сейчас в БД есть таблица `speakers`, но эндпоинтов нет;
  - назначение спикера: `api-gaps` предлагает `PUT /jobs/{id}/speakers/{slot}` с областью `slot` или `segment` (индекс сегмента); интерфейс делает и то и другое, а ещё «все сегменты по имени», которое на уровне API не описано. Заглушка хранит ручные назначения по сегментам;
  - `GET /jobs/{id}` должен отдавать сопоставление слот → спикер (`speaker_assignments`) и ручные назначения по сегментам;
  - **вопрос к продукту:** должна ли шапка «Speakers» отражать ручные назначения (в макете нет), или показывать реальных спикеров записи?
- **Заглушка записи 6** (с AI-подсказками в макете): её слоты по-прежнему «Speaker N» серым, пока не будут сделаны подсказки (итерация 7).

#### Итерация 7: что важно знать

- **Отклонения от макета:**
  - отклонённая подсказка спикера возвращает слот к серому цвету; в макете цвет подсказки оставался из-за того, что он брался из статичных данных (по `design.md` слот окрашен цветом подсказки только пока она ожидает решения);
  - подсказки не возвращаются при повторном открытии (в макете они каждый раз «оживали» заново, причём принятые спикеры терялись, а принятые теги оставались).
- **Название разбирается только целиком.** Подсказка названия есть лишь в баннере: принять или отклонить её можно только через «Accept all» или «✗». Отдельных кнопок нет ни в макете, ни в `design.md`. Открытый вопрос: нужны ли?
- **Поведение при разборе по одной:** даже когда разобраны все теги и спикеры, баннер остаётся, пока не принято или не отклонено название.
- **Рамки браузера.** Chrome округляет рамку `1.5px` вниз до целых пикселей устройства, поэтому у «призрачных» элементов она на самом деле 1 px на обычном экране. `DashedBorder` делает то же (`floor(width × dpr) / dpr`), иначе элементы получались на 1 px крупнее; баннер сделан `Container`, а не `DecoratedBox`, чтобы рамка занимала место.
- **Требования к серверу (api-gaps §1.2, §2.4, §4.1–4.2), всё ещё TBD:**
  - таблица подсказок (одна запись на запись, удаляется, когда разобрано всё) и эндпоинты `POST /jobs/{id}/suggestions/accept-all`, `dismiss-all`, `tags/{label}/accept|reject`, `speakers/{slot}/accept|reject`; каждый возвращает обновлённые подсказки или `null`;
  - в подсказке для тега макет держит цвет, для спикера имя и цвет; вопрос про цвет тега (хранится или считается на клиенте) по-прежнему открыт;
  - принятие тега создаёт его в библиотеке, если такого нет; принятие спикера создаёт спикера и подтверждает слот (это то же сопоставление «слот → спикер», что нужно Speaker Picker, см. итерацию 6);
  - Gemini: одним вызовом (саммари + подсказки) или двумя, решение ждёт замеров качества и задержки (api-gaps §4.2).
- **Что заглушка не делает:** подсказки есть только у одной записи, как в макете; на других записях баннера нет.

#### Итерация 8: что важно знать

- **Отклонения от макета:**
  - счётчики и чипы считаются по данным, а не берутся из статичного макета: у `meeting` в макете «3 files», в заглушке реальных записей 2, поэтому и «used in N files» в подзаголовке другое;
  - имя тега приводится к нижнему регистру (как при создании из дропдауна детали); повторное имя не принимается: под полем красный текст «A tag with this name already exists.» (в макете дубликаты не проверялись);
  - Enter в поле имени сохраняет; пустое имя ничего не делает (как в макете);
  - в тексте удаления правильное число: «1 transcription» / «2 transcriptions» (в макете «transcription(s)»);
  - удаление тега убирает его у всех записей и из фильтра списка; переименование меняется во всех записях.
- **Рамки и высоты.** Рамка плитки — `DashedBorder` шириной 2 с привязкой к пикселям устройства; footer модалки растягивает кнопки по высоте самой высокой, как flex-строка; подпись поля — строка 14 px (Chrome округляет вверх).
- **Требования к серверу (api-gaps §1.2, §2.1):**
  - `GET /tags` должен возвращать для каждого тега `id`, `label`, описание, цвет (вопрос про хранение цвета всё ещё открыт) и список записей (`id` + название, достаточно первых двух и счётчика);
  - `POST /tags`, `PUT /tags/{id}` (переименование и описание), `DELETE /tags/{id}` с ответом «сколько записей затронуто», уникальность `label` без учёта регистра (сервер тоже должен отвечать 409, клиент проверяет только по загруженной библиотеке);
  - описание тега нужно Gemini для автопометки и подсказок (итерация 7): его нужно передавать в промпт.

#### Итерация 9: что важно знать

- **Отклонения от макета:**
  - число файлов и время считаются по данным заглушки: в макете у Alexei «4 files · 42 min», у нас 3 записи и 1h 9min. Время — **сумма длительностей записей**, а не время речи спикера (в макете, видимо, речь): для реального времени нужны данные по сегментам;
  - учитываются только записи со статусом `done`; спикер «участвует» в записи, если он подтверждён для слота диаризатора (в пределах числа спикеров записи) или назначен вручную на сегмент;
  - плейсхолдер описания: «Role, topics, how they talk…» (в макете у спикера остался «Describe when this applies…» от тега);
  - имя спикера уникально без учёта регистра («A speaker with this name already exists.»), регистр сохраняется как введён; Enter сохраняет, пустое имя ничего не делает;
  - правильное число в тексте удаления («1 transcription»).
- **Требования к серверу (api-gaps §1.3, §2.2):** `GET/POST/PUT/DELETE /speakers` с `description`, цветом, списком записей (id + название) и суммарным временем; удаление отвечает числом затронутых записей; переименование не должно ломать сопоставления слотов и ручные назначения (при хранении по `speaker_id` это бесплатно, при хранении по имени нужно обновлять). Описание нужно Gemini для автоопределения голосов (§4.2).

#### Итерация 10: что важно знать

- **Отклонения от макета:**
  - кнопка Upload в диалоге неактивна, пока не выбран подходящий файл (в макете она ничего не делает);
  - выбранный файл показывается в зоне (иконка, имя, размер, «click to choose another file»), при неподходящем файле — причина красным;
  - выпадающие списки — стандартные `DropdownButton` Flutter, а не нативный `<select>`: размеры поля совпадают, но само выпадающее меню выглядит по-другому (пункты выше, серая подсветка выбранного);
  - при перетаскивании берётся первый файл, несколько сразу не поддерживаются;
  - после загрузки открывается список записей и сбрасываются поиск/фильтры, чтобы новая запись была видна.
- **Мок «жизни» задания:** статус считается по времени, прошедшему с загрузки, в момент запроса данных (без таймеров в репозитории), поэтому тесты детерминированы: без `JobTiming` запись остаётся `pending`. Длительность новой записи выдумана (~1 минута на мегабайт), после `done` число спикеров — из выбора в диалоге («Auto-detect» = 2).
- **Опрос:** пока в загруженном списке есть `pending`/`processing`, список перезапрашивается по таймеру. Записи из макета (id 1 и 3) не меняются никогда, поэтому в моке опрос идёт постоянно; в проде он остановится, когда всё завершено. Для реального сервера лучше SSE/WebSocket или увеличивающийся интервал.
- **Требования к серверу:**
  - `POST /transcriptions` (сейчас загрузка идёт через старый multipart `/api/...` в `ApiClient`): кроме файла принимать `language` (`auto|en|ru`), `summary` (`auto|short|full|none`), `speakers` (`auto|1|2|3|4+`); ответ — созданная запись со статусом `pending`;
  - лимит 400 MB и список форматов должны проверяться и на сервере (клиент проверяет только имя и размер);
  - для загрузки в GCS нужен поток байт: `ChosenFile` сейчас хранит только имя и размер, при подключении API добавить чтение содержимого (`file_picker` с `withReadStream`/`withData` или `XFile.openRead()` для drag-and-drop);
  - опции Summary и Speakers должны доходить до Gemini/диаризатора (не реализовано ни в gateway, ни в transcriber: проверить `api-gaps.md` §1.1, §4.2).
- **Зависимости:** добавлены `desktop_drop` (перетаскивание файла на веб-странице) и `cross_file` (тип `XFile` из событий перетаскивания). Перетаскивание проверено только сборкой, но не вручную: в автотестах и headless-Chrome его не воспроизвести.
