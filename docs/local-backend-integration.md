Рабочий документ ветки `redesign` (ветку не меняем). Он описывает, **как мы будем доводить новый интерфейс до работы с настоящим gateway**, ничего не выкатывая на прод: локальное окружение, что и почему в нём заменяется, порядок срезов и защита продакшена.

## 1. Цель и ограничения

**Цель.** Гонять Flutter-клиент против настоящего gateway и дорабатывать API итеративно, синхронизируя с экранами. Нужен повторяемый процесс: «доработали API → доработали клиент → проверили в браузере → повторили».

**Ограничения (заданы владельцем):**

- **Всё локально.** На проде ничего не разворачиваем и не проверяем. Пока идёт работа, всё остаётся в ветке `redesign`.
- **Разворачиваем минимум.** Не нужны ни Telegram-бот, ни GPU, ни Cloud Run, ни бакет. Из «настоящего» нужны только Postgres и сам gateway.
- Postgres живёт постоянно и накапливает данные между запусками; gateway и Flutter обновляются итеративно.
- Прод-конфигурация и прод-поведение gateway **не меняются**: всё локальное включается только профилем Spring `local` и по умолчанию выключено.

## 2. Как это устроено сейчас (факты)

### 2.1. Что нужно gateway, чтобы работать

| Зависимость | Что в коде | Для локалки |
|---|---|---|
| **Postgres** | Flyway накатывает миграции на пустую БД при старте (`spring.flyway.enabled: true`, 29 файлов `V*.sql`) | Достаточно одного контейнера, БД может быть пустой |
| **Авторизация** | `JwtAuthFilter` кладёт `authenticatedUserId` в запрос, если есть валидный Bearer-токен. Загрузка (`POST /transcribe`) без токена работает от «анонимного» пользователя (`resolveAnonymous()`). **Но `GET /transcriptions` без токена отвечает 401** | Решено: локальный фильтр в профиле `local`, см. 4.6 |
| **Хранилище аудио** | Интерфейс `AudioStorage`, **единственная реализация** `GcsAudioStorage` — `@Component` без условий, использует `StorageOptions.getDefaultInstance()` (учётные данные Google) | Нужна подмена, см. 4.2 |
| **Transcriber** | `TranscriberClient` — конкретный класс без интерфейса; gateway использует только `submitByReference` (по `storage_uri`) | Нужна подмена, см. 4.1 |
| **Gemini** | `SummarizerConfig`: без ключа автоматически `NoopSummarizer` | Ничего делать не нужно |
| **CORS** | Не настроен; в проде его заменяет nginx (`/api/*` → gateway со срезом `/api`) | Нужен прокси dev-сервера Flutter, см. 4.5 |
| **Фоновые задачи** | `@EnableScheduling`: `DatabaseBackupService` (бэкап таблиц в GCS, cron `0 45 16 * * *`) и `StorageMaintenanceService` (очистка «осиротевших» объектов бакета, cron помечен как «TEMPORARY for testing») | Отключить в `local`, см. 4.2 |

### 2.2. Контракт transcriber

Gateway общается с transcriber тремя вызовами:

| Эндпоинт | Что делает |
|---|---|
| `POST /transcribe?storage_uri=gs://…&model=small&diarize=true&language=ru&num_speakers=3` | Принимает задание, сразу отвечает `202 {"job_id": "…"}` |
| `GET /jobs/{job_id}` | Статус, прогресс и (когда готово) результат. Gateway опрашивает раз в 5 секунд (`dictara.transcriber.poll-interval-ms: 5000`) |
| `GET /health` | `{"status":"ok", ...}` |

Статусы: `pending` → `processing` → `done` или `failed`. Внутри `processing` две фазы: `transcribing` и `diarizing`.

Ответ в процессе работы:

```json
{"status": "processing", "result": null, "error": null, "retryable": true,
 "elapsed_s": 12.4,
 "progress": {"processed_s": 310.0, "total_s": 862.0, "phase": "transcribing", "diarize_progress": null}}
```

Ответ по готовности:

```json
{"status": "done", "duration_s": 41.2,
 "result": {"language": "en", "audio_duration_s": 862.0,
   "segments": [
     {"start": 0.0,  "end": 34.1, "text": "Good morning everyone…", "speaker": "SPEAKER_00"},
     {"start": 34.1, "end": 72.3, "text": "Right. So Q2 was solid…", "speaker": "SPEAKER_01"}
   ]}}
```

Ошибка: `{"status": "failed", "error": "…", "retryable": false}` (флаг `retryable` gateway использует для решения о повторе).

Всё, что уже нарисовано во Flutter (пульсирующий прогресс «41% — transcribing…», фаза diarizing, вкладка Transcript со спикерами, статусы), питается именно этим контрактом.

### 2.3. Хранилище аудио: кто что вызывает

| Операция `AudioStorage` | Кто вызывает | Что делает |
|---|---|---|
| `upload` | `TranscribeController` | Кладёт файл в `gs://bucket/audio/<дата>/<id>/<имя>`, считает SHA-256 (по нему работает дедупликация) |
| `download` | `ExportController` | Отдаёт аудио при экспорте архива «With audio» |
| `listObjects`, `delete` | `StorageMaintenanceService` (по расписанию) | Чистит «осиротевшие» объекты бакета |
| `uploadBytes` | `DatabaseBackupService` (по расписанию) | Ежедневный бэкап таблиц БД в бакет |

### 2.4. Что было раньше (история)

До коммита `62003da` (июнь 2026) существовал `DatabaseAudioStorage`: байты файла писались в таблицу `audio_content` (`bytea`), ссылка `AudioRef.Db(id)` означала «искать в БД», включался условием «бакет не задан» как локальный запасной вариант. Его удалили (весь прод перенесли в GCS), а миграция `V14__drop_audio_content.sql` удалила таблицу. Просто откатить нельзя: интерфейс с тех пор вырос (хэш, `listObjects`, `delete`, `uploadBytes`), `AudioRef` стал простым `data class` со ссылкой-строкой, а вернуть таблицу обычной миграцией значило бы вернуть мёртвую таблицу в прод-схему.

### 2.5. Существующие эндпоинты gateway

Уже есть (пригодятся первым срезам): `GET /transcriptions` (список: `job_id`, `file_name`, `title`, `created_at`, `status`, `tags`), `GET /jobs/{jobId}`, `POST /jobs/{jobId}/tags`, `DELETE /jobs/{jobId}/tags/{tag}`, `PATCH /jobs/{jobId}/title`, `GET /transcript`, `GET /export`, `POST /transcribe`, `GET /formats`, `GET /health`, а также `/auth/*` и `/telegram/*` (для бота). Библиотек тегов и спикеров, подсказок, структурного саммари и т. д. нет — это содержание срезов (см. [api-gaps.md](api-gaps.md)).

### 2.6. Как деплоится прод

`.github/workflows/ci.yml`: на любой `push` в `master` собираются образы (gateway, tg-bot, app-material) по фильтрам путей и по SSH выкатываются на сервер. Образы публикуются **только с тегом `:latest`**. Job `test` запускает тесты gateway, tg-bot и transcriber, но **не запускает `flutter analyze` и `flutter test`**. Flutter-образ собирается с `FLUTTER_TARGET=lib/material/main_material.dart`, то есть весь редизайн уйдёт в прод целиком при мерже.

### 2.7. Как тесты gateway работают с БД

В CI и локально тесты берут временный Postgres через **Testcontainers** (случайный порт, исчезает после прогона), поэтому dev-данные они не затрагивают. Переменные `TEST_DB_URL/USERNAME/PASSWORD` — устаревший обходной путь (коммит `caad6ff`, 23 июня): тогда Testcontainers 1.20.4 не работал с новым Docker Desktop. Это уже исправлено подъёмом Testcontainers до 1.21.4 (все 75 тестов gateway проходят на Testcontainers). Раздел «Running integration tests locally» в `gateway/CLAUDE.md` устарел. Тесты делают `TRUNCATE audio_meta CASCADE` — против dev-БД их запускать нельзя, и не нужно.

## 3. Схема локального окружения

```
Flutter (flutter run, :3001)
   │  /api/* → прокси dev-сервера (web_dev_config.yaml), срезает /api
   ▼
Gateway (gradlew bootRun / IntelliJ, профиль local, :8080)
   ├── Postgres (docker, :5432, БД dictara_dev, свой volume, всегда поднят)
   ├── TranscriberPort → заглушка на Kotlin внутри gateway (5–6 сценариев)
   └── AudioStorage   → LocalDbAudioStorage (байты в Postgres)
```

Не поднимаются: Telegram-бот и telegram-bot-api, transcriber, Prometheus/Loki, nginx, бакет GCS.

## 4. Решения по компонентам

### 4.1. Transcriber: интерфейс и заглушка внутри gateway

**Решение.** Выделить интерфейс клиента transcriber (`TranscriberPort`, по образцу уже существующих `SummarizerPort` / `NoopSummarizer` / `SummarizerConfig`) и две реализации, выбираемые профилем Spring:

- настоящая — текущий `TranscriberClient` (по умолчанию, поведение прода не меняется);
- заглушка — профиль `local`.

Заглушка пишется на Kotlin **внутри gateway** (не отдельный сервис). В неё зашито **5–6 готовых сценариев, все успешные**, с правдоподобными данными как в макете (звонок с тремя спикерами, интервью, лекция, голосовая заметка без спикеров и т. п.); сценарий на каждое задание выбирается случайно.

**Что рассматривали.** Настоящий transcriber локально (первый запуск ~15 минут, модели 4–5 ГБ, медленно на CPU, диаризация требует `HF_TOKEN`, а для `gs://` всё равно нужен GCS) — отвергнут; Cloud Run (деньги, прод-бакет) — отвергнут; отдельная заглушка на Python/FastAPI или WireMock — не выбрана в пользу Kotlin в самом gateway.

**Детали реализации.**

- Прогресс заглушка вычисляет **от времени, прошедшего с отправки задания** (как наш `FakeTranscriptionRepository`): без таймеров и потоков; gateway опрашивает раз в 5 с, значит проценты меняются шагами по 5 с.
- Отдаёт то же, что настоящий transcriber: `pending` → `processing` (сначала фаза `transcribing`, затем `diarizing`) → `done` с `segments` (`start`, `end`, `text`, `speaker` как `SPEAKER_00`…), `language`, `audio_duration_s`, `duration_s`.
- Тайминги по умолчанию быстрые (порядка нескольких секунд очереди и ~15–20 с обработки), настраиваются свойствами.
- `storage_uri` заглушке не нужен: ничего не скачивает.

**Следствия.** Заглушка попадает в прод-jar, но выключена и не создаётся без профиля `local`. Состояние `failed` локально не проверить (все сценарии успешные): при необходимости позже добавить «падающий» сценарий. Настоящий HTTP-клиент по-прежнему покрыт существующими тестами с WireMock — их не трогаем. Настоящий transcriber остаётся доступным (`docker compose --profile local`) для разовых проверок.

### 4.2. Хранилище аудио: LocalDbAudioStorage

**Решение.** Новая реализация `AudioStorage` для профиля `local`: **байты хранятся в Postgres**, ссылки вида `db://audio/<дата>/<id>/<имя>` (и `db://backups/…`). Реализуются все пять операций (`upload` с SHA-256, `download`, `listObjects`, `delete`, `uploadBytes`), ~30–40 строк на `JdbcTemplate`.

**Почему не файлы на диске и не эмулятор.** Всё состояние в одной БД: сбросили БД — сбросилось и аудио, нет «осиротевших» файлов; не нужны volume и права на папку; работает и при `bootRun`, и в docker. Эмулятор `fake-gcs-server` (без правок кода, но лишний контейнер и настройка бакета) и dev-бакет в настоящем GCS (риск очистки «сирот» не того бакета) отвергнуты.

**Таблица.** Создаётся **повторяемой миграцией Flyway** `R__local_audio.sql` в отдельной папке `db/local`, которую подключает только `application-local.yaml` (`spring.flyway.locations: classpath:db/migration,classpath:db/local`). Нумерованные `V…` для локальных таблиц использовать **нельзя**: когда в основной папке появятся новые прод-миграции с меньшим номером, локальная БД будет ругаться на порядок. Обычная миграция в основной папке тоже не подходит: таблица появилась бы на проде.

**Сопутствующее.**

- `DatabaseBackupService` и `StorageMaintenanceService` в профиле `local` **отключены** (`@Profile("!local")`).
- **Guard:** профиль `local` не стартует, если задан `GCS_UPLOADS_BUCKET`. Причина: очистка «сирот» удаляет из бакета всё, на что нет ссылок в БД; в пустой локальной БД ссылок нет, то есть подключённый по ошибке прод-бакет был бы очищен целиком.

### 4.3. Как запускать gateway и Postgres

**Gateway.** На хосте: `./gradlew bootRun --args="--spring.profiles.active=local"` или конфигурация запуска в IntelliJ. Быстрый цикл «правка → перезапуск», отладчик. В `build.gradle.kts` добавить `spring-boot-devtools` в `developmentOnly` (в прод-jar не попадает). Docker-образ gateway собираем **перед мержем** как дымовую проверку (как в проде).

**Postgres.** Отдельный файл **`docker-compose.dev.yml`** (не `docker-compose.override.yml`: тот подхватывается автоматически) в корне репозитория:

- имя проекта `dictara-dev`, контейнер `postgres:16`, БД `dictara_dev`, порт `127.0.0.1:5432`, собственный именованный volume, `restart: unless-stopped` (поднят постоянно);
- пароль по умолчанию совпадает с `application.yaml` (`dictara_dev`), поэтому для запуска не нужен `.env`;
- без секретов.

**Скрипты.** Тонкий `scripts/dev.ps1` (поднять Postgres, дождаться готовности, запустить gateway в профиле `local`) и скрипт сброса dev-БД (пересоздать volume). Предпочтений по форме запуска не было: реализуем минимально.

**Тесты gateway** остаются на Testcontainers, `TEST_DB_*` не задаём (см. 2.7). Отдельная БД `dictara_test` не нужна.

### 4.4. Данные в локальной БД (сид)

**Решение.** Сид — **SQL, повторяемая миграция `R__seed.sql`** в `db/local`. Данные по макету: записи разных статусов, теги с описаниями и цветами, спикеры с описаниями, связи, сегменты транскрипта, саммари, подсказки (по мере появления таблиц). Набор данных сида **независим** от сценариев заглушки transcriber.

**Идемпотентность.** Повторяемая миграция выполняется заново **каждый раз, когда файл изменился**, а не только на пустой БД. Сид будет расти вместе с API (на каждом срезе дописываем данные для нового экрана), поэтому писать его нужно идемпотентно: **фиксированные UUID и `INSERT … ON CONFLICT DO NOTHING`**. Так «сидить на пустой БД» получается само собой, а новые данные дозаливаются без сброса. Несовместимое изменение схемы — повод сбросить БД скриптом.

**Цена выбора SQL.** При изменениях схемы сид приходится править вручную (в отличие от сидера на Kotlin, где ошибку показал бы компилятор). Принято осознанно.

**Отвергнуто:** сидер на Kotlin (`ApplicationRunner`); загрузка через UI при каждом сбросе; дамп прода (данные реальных пользователей).

### 4.5. Связь Flutter → gateway

**Решение.** Прокси в dev-сервере Flutter. Проверено по исходникам установленного Flutter (3.47): dev-сервер читает файл **`web_dev_config.yaml`** (`flutter_tools/lib/src/web/devfs_config.dart`, правила прокси — `devfs_proxy.dart`), поддерживаются правила с `prefix`/`regex`, `replace` и `target`. Черновик правила, повторяющего nginx (`rewrite ^/api/(.*) /$1`); точный синтаксис `replace` проверить на деле:

```yaml
server:
  proxy:
    - prefix: /api/
      replace: /
      target: http://localhost:8080
```

Так пути в коде приложения остаются как в проде (`/api/...`, `ApiClient._base = '/api'`), gateway не меняется, CORS не нужен. Отвергнуто: CORS в gateway под профилем `local` (лишний код, разные базовые пути) и nginx в docker (лишний контейнер).

### 4.6. Авторизация: локальный dev-пользователь

**Что решено.** На этом этапе без входа через Telegram; экран логина в новом интерфейсе отложен отдельной задачей.

**Проблема.** «Анонимный пользователь» (`resolveAnonymous()`) работает только для загрузки. `GET /transcriptions` (первый срез) без токена отвечает **401**, поэтому запросам из Flutter нужен пользователь.

**Решение — вариант A: локальный фильтр авторизации в профиле `local`.** Небольшой компонент, существующий только при профиле `local` (`@Profile("local")`): если в запросе нет валидного токена, он проставляет `authenticatedUserId` фиксированного **dev-пользователя**. Этого пользователя создаёт сид (`R__seed.sql`, фиксированный UUID), ему принадлежат все сидовые данные, и он же владелец всего, что загружено через UI.

- Во Flutter про авторизацию ничего нет: запросы идут без `Authorization`.
- Настоящий `JwtAuthFilter` не меняется; если токен пришёл и валиден, он имеет приоритет.
- Компонент не создаётся без профиля `local`, поведение прода не меняется. В автотест «профиль `local` не утёк в прод» (5.1) стоит включить и его.
- Когда дойдёт очередь до входа через Telegram, фильтр можно отключить флагом, ничего не меняя в остальном коде.

**Отвергнуто:** B (dev-JWT через `--dart-define`: код авторизации во Flutter, токен нужно генерировать и обновлять) и C (сразу вход через бот: нужны токены и бот, для проверки экранов не нужно).

### 4.7. Как переключаться между моками и бэкендом

Для миграции экраны переводятся на реальный API по срезам, поэтому на время работы нужен переключатель: `--dart-define=BACKEND=mock|local`. По умолчанию — `mock` (как сейчас); `main_material.dart` выбирает `FakeTranscriptionRepository` или `HttpTranscriptionRepository`, экраны разницы не знают. Так можно в любой момент сравнить «макет на моках» и «то же на реальном API».

**Итог для моков:** после перевода всех срезов моки убираются из запускаемого приложения, но `FakeTranscriptionRepository` **остаётся как тестовый двойник** (переезжает в `test/`): на нём держатся 178 виджет-тестов, и он служил эталоном «как в макете». Полностью удалять его нельзя без переписывания тестов под HTTP-заглушки.

### 5.1. Карта рисков

| Риск | Откуда | Статус |
|------|--------|--------|
| `local` подключился к боевой БД (например, через SSH-туннель; в `gateway/CLAUDE.md` он упомянут) | Сид и миграции ушли бы на прод | **Принято:** в профиле `local` gateway не стартует, если хост БД не `localhost`/`127.0.0.1` или имя БД не `dictara_dev` |
| `local` подключился к прод-бакету | Очистка «сирот» удалила бы прод-аудио | **Принято** (4.2): `local` не стартует при заданном `GCS_UPLOADS_BUCKET`; плюс фоновые задачи в `local` выключены |
| `local` дотянулся до боевого transcriber | Расходы, загрязнение прода | Отдельной проверки не берём: в `local` вместо HTTP-клиента работает заглушка, адрес ей не нужен |
| Боевые секреты попали в dev-запуск | Корневой `.env` | Отдельной защиты не берём: `bootRun` читает только переменные окружения, `.env` читает `docker compose`; в `docker-compose.dev.yml` секретов нет |
| Профиль `local` «утёк» в прод (активны заглушки или локальные миграции) | Ошибка конфигурации | **Не выбрано.** Предложение: автотест, что без `local` активны `GcsAudioStorage` и HTTP-клиент transcriber, нет локального фильтра авторизации, а `db/local` не входит в `flyway.locations` |
| Случайный деплой | Любой push в `master` выкатывает всё без подтверждения (`ci.yml`) | **Не решено.** Предложено: branch protection на `master` (только PR и обязательные проверки, ручной мерж); локальный pre-push хук против push в `master` |
| Сломанный Flutter проходит CI | В `ci.yml` нет `flutter analyze` и `flutter test` | **Не решено.** Предложено: добавить оба шага в job `test` (178 тестов идут на Dart VM за ~10 с) |
| Ломающая миграция | Flyway накатывает миграции при старте на проде, они односторонние | **Не решено.** Предложено: линтер миграций в CI (DROP, RENAME, смена типа, `SET NOT NULL` без default, с явным исключением через комментарий) и репетиция новых миграций на схеме прода (`pg_dump --schema-only` → пустая БД) |
| Нечем откатиться | Образы публикуются только с тегом `:latest` | **Не решено.** Предложено: дополнительно тегировать образы по sha коммита; перед первым мержем с миграциями делать `pg_dump` прод-БД (сейчас есть только ежедневный JSON-бэкап в GCS) |
| Поломка старых клиентов | Прод-приложение и `tg-bot` ходят в те же эндпоинты | Правило (5.2): миграции и API только аддитивные. Автоматической проверки нет |
| Весь редизайн заменяет прод-UI за один мерж | `app/**` пересобирает `app-material` | **Решим потом.** Варианты: отдельный beta-адрес (второй образ/поддомен/путь), big-bang, feature flag в приложении |

**Пункты со статусом «Не решено» нужно закрыть до первого мержа в `master`.** Пока они не закрыты, работа идёт только в ветке `redesign`. Пункты, помеченные «Предложено», изменяют только `ci.yml` и настройки GitHub; без явного согласия владельца их не трогаем.

### 5.2. Правила, действующие уже сейчас

- Миграции только **аддитивные** (новые таблицы и колонки; без удаления и переименования), старые эндпоинты остаются, пока в проде жив старый Flutter-клиент и `tg-bot`.
- Все локальные конструкции (профиль `local`, `db/local`, заглушка transcriber, `LocalDbAudioStorage`, сид) выключены по умолчанию и не меняют поведение прод-сборки.
- Не запускать интеграционные тесты gateway против dev-БД (они делают `TRUNCATE`); не задавать `TEST_DB_*`.
- Не называть dev-compose `docker-compose.override.yml`; не менять прод-`docker-compose.yml` ради локальной работы.
- Пуш в `master` = деплой и накат миграций на прод. Не пушить в `master` без явного решения.

## 6. Срезы интеграции

Порядок: **список + деталь → теги → спикеры → загрузка → AI-подсказки.** Обоснование: чтение уже частично есть в gateway, первый срез проходит быстро и проверяет весь конвейер; подсказки требуют новой таблицы и Gemini, поэтому последние.

**Что такое срез.** Вертикальная порция: (1) миграция и эндпоинт в gateway с интеграционным тестом → (2) метод в `HttpTranscriptionRepository` (интерфейс `TranscriptionRepository` уже есть) → (3) проверка экрана в браузере против `local` → (4) данные для экрана в сид.

|------|--------|------------------------|-----------------------------------------------------------|
| 1. Список + деталь | Transcriptions, детали, вкладки Transcript/Overview | `GET /transcriptions`, `GET /jobs/{id}` | Фильтры и сортировка списка (`sort`, `status`, `tag_ids`, `q`), в списке спикеры/длительность/прогресс, в детали `original_filename`, размер, язык, число слов, структурное саммари (сейчас один текстовый блок); dev-пользователь в `local` (4.6) |

### Итерация 0: что важно знать

**Как запустить.** Нужны Docker и Gradle 8.7 в `PATH` (версия как в CI).

```powershell
scripts\dev.ps1            # Postgres в Docker + gateway (gradle bootRun, профиль local), :8080
scripts\dev.ps1 -DbOnly    # только Postgres, gateway запускаете из IntelliJ с профилем local
scripts\dev-reset.ps1      # выбросить dev-БД и создать пустую (gateway должен быть остановлен)
```

Ctrl+C останавливает gateway; Postgres остаётся поднятым (`restart: unless-stopped`). Профиль `local` — `SPRING_PROFILES_ACTIVE=local` или `--spring.profiles.active=local`.

**Что сделано (`gateway/`, `docker-compose.dev.yml`, `scripts/`):**

- `port/TranscriberPort.kt`: интерфейс и модели `TranscribeParams`/`TranscriberJobSnapshot` (переехали из `client/`); `OrchestratorService` зависит от порта. `TranscriberClient` реализует порт и помечен `@Profile("!local")`.
- `adapter/StubTranscriber.kt`: 6 сценариев (квартальный обзор на 3 спикера, собеседование, синк, лекция, голосовая заметка, разговор на русском); прогресс считается от времени с момента отправки (по умолчанию 2 с `pending`, 10 с `transcribing`, 5 с `diarizing`, настраивается `dictara.local.stub.*`); без диаризации спикеров в сегментах нет; `num_speakers` ограничивает число меток.
- `storage/LocalDbAudioStorage.kt` + `db/local/R__local_audio.sql`: байты в таблице `local_audio_objects`, ссылки `db://audio/<дата>/<id>/<имя>`.
- `GcsAudioStorage`, `DatabaseBackupService`, `StorageMaintenanceService` — `@Profile("!local")`.
- `filter/LocalDevAuthFilter.kt`: без токена запрос идёт от dev-пользователя `00000000-0000-4000-8000-000000000001` (создаётся `R__seed.sql`, план `unlimited`, чтобы не упираться в лимит бесплатного плана).
- `config/LocalProfileGuard.kt` (`EnvironmentPostProcessor`, зарегистрирован в `META-INF/spring.factories`): при профиле `local` отказывается стартовать, если хост БД не `localhost`/`127.0.0.1`, имя БД не `dictara_dev` или задан `GCS_UPLOADS_BUCKET`. Проверка сделана постпроцессором окружения, а не бином, намеренно: бин создаётся уже после Flyway, то есть миграции и сид успели бы выполниться на чужой БД. Обойти проверку нельзя.
- `application-local.yaml`: БД `dictara_dev`, Flyway `db/migration` + `db/local`, опрос transcriber раз в секунду, dev-секрет JWT, тайминги заглушки.
- `build.gradle.kts`: `spring-boot-devtools` в `developmentOnly`.

**Проверено.**

- Тесты gateway: 105 из 105 (было 75; добавлено 30: `LocalProfileGuardTest` 10, `StubTranscriberTest` 8, `LocalDbAudioStorageTest` 7, `LocalProfileIntegrationTest` 5). Интеграционный тест поднимает весь контекст с профилем `local` на своём Postgres с БД `dictara_dev`: seed, загрузка через `POST /transcribe` до `done` на заглушке, дедупликация, аудио в БД, `GET /transcriptions` без токена.
- Вручную: `scripts\dev.ps1` поднимает окружение; `GET /health` отвечает; загрузка файла проходит `processing` (фазы `transcribing` и `diarizing` с процентами) → `done`; `GET /transcriptions` без токена возвращает загруженную запись.
- Guard проверен запуском: с `SPRING_DATASOURCE_URL=…/dictara` и заданным `GCS_UPLOADS_BUCKET` gateway не стартует и объясняет обе причины.

**Что выяснилось по ходу.**

- В `application.yaml` секрет JWT по умолчанию (`changeme-set-in-env`, 19 символов) короче требуемых JJWT 32: без переменной `JWT_SECRET` gateway не стартует. Тесты этого не замечали (у них свой `jwt.secret`). Для `local` в `application-local.yaml` задан dev-секрет.
- Gradle-обёртка `gateway/gradlew` указывает на Gradle 9.6.0, а проект собирается на 8.7 (CI, Dockerfile). Поэтому скрипты используют `gradle` из `PATH`. Приведение обёртки к 8.7 или явное решение — отдельная задача.
- Windows PowerShell 5.1 превращает вывод в stderr нативных команд (у `docker` там прогресс) в ошибки, если включён `$ErrorActionPreference = 'Stop'`: в скриптах он не включён, успех проверяется по `$LASTEXITCODE`.
- Спикеры в результате заглушки — `SPEAKER_00`, `SPEAKER_01`…, как у настоящего transcriber (модель `Segment.speaker`).
- Devtools подключён, но автоперезапуск при пересборке отдельно не проверялся.

**Что сделано (`app/`):**

- `web_dev_config.yaml`: правило `prefix: /api/`, `replace: /`, `target: http://localhost:8080`, то же, что делает nginx в проде.
- `lib/data/gateway_client.dart`: `GatewayClient` (JSON поверх `package:http`, база `/api`), `GatewayException` (нет ответа / код ошибки / не JSON; сообщение берётся из поля `message` ответа Spring).
- `lib/data/http_transcription_repository.dart`: `HttpTranscriptionRepository`. Работают `list()` и `tags()`; остальные методы бросают `NotIntegratedException` с номером итерации, которая их подключит. Список пока **временный**: gateway отдаёт `job_id`, `file_name`, `title`, `created_at`, `status`, `tags` и не умеет фильтровать, поэтому фильтры и сортировка выполняются на клиенте (общий `filterTranscriptions`), `tags()` собирается из тегов записей, цвет тега считается по хэшу имени (`colorForLabel`, как решено в `api-gaps.md`).
- `lib/material/main_material.dart`: переключатель `BACKEND=mock|local` (неизвестное значение — ошибка при старте). Опрос списка каждые 3 с при `local`.

**Изменения модели, нужные для настоящего API:**

- `id` записи стал `String` во всём клиенте (в gateway это UUID; в макете и моках было `int`). Заглушка хранит числовые строки `'0'`…`'6'`, порядок «новые сверху» по-прежнему по числу. Закрывает пункт «Тип `Job.id`» из «Известных проблем» в `redesign-plan.md`.
- Новый статус `TranscriptionStatus.failed` (значок ошибки, «Failed», цвета `danger`): gateway отдаёт `failed`, в макете этого состояния нет. Строка не кликается (как `pending`/`processing`); в фильтре списка появился пункт «Failed». Статус gateway `summarizing` показывается как `processing`.
- `Transcription.duration` может быть неизвестной (`Duration?`): в списке gateway длительности нет. Строка тогда её не показывает; в шапке и Overview подставляется 0. Для `processing` без процента строка пишет «Processing…», а не «0%».

**Проверено:** 204 теста Flutter (было 178; добавлено 26: клиент и репозиторий на `MockClient` 21, строка и статус 5), `flutter analyze` чист. Вручную: прокси отвечает; приложение на `BACKEND=local` показывает записи, загруженные в gateway (статусы `Done` и `Processing`).

**Что пока не работает при `BACKEND=local`** (по замыслу, экраны подключаются по итерациям): страницы Tags (4), Speakers (5), открытие записи и переименование (3), загрузка через диалог Upload (7), AI-подсказки (8). Такие вызовы бросают `NotIntegratedException`, страница остаётся пустой, а ошибка видна в консоли браузера; понятное сообщение на экране можно сделать при подключении первого такого экрана.

### Итерация 2a: что важно знать

**Решения (обсуждены с владельцем):**

- **Пагинация со смещением средствами Spring, а не курсором.** Личный список в десятки-сотни записей, курсор избыточен и сложен для сортировок по длительности и названию. Недостаток смещения (дубль или сдвиг границы страниц, когда сверху добавляют запись) лечится двумя простыми вещами: клиент не добавляет запись с уже известным id, а опрос перезапрашивает уже загруженное одним запросом «страница 0, размер = столько, сколько показано».
- **Совместимость.** Без `page`/`size` `GET /transcriptions` отдаёт прежний массив (его читает продовый клиент, он ждёт `tags` списком строк, поэтому тип менять нельзя). Если передан `page` или `size`, ответ `{"items": [...], "page": 0, "size": 30, "has_next": true}`. После отключения старого клиента можно сделать пагинацию обязательной.
- **Названия параметров:** `page` (с 0) и `size` (по умолчанию 30, максимум 500; вне 1..500 или `page < 0` ответ 400) в стиле Spring.
- **Бесконечная прокрутка** по 30 записей (`transcriptionPageSize`).

**gateway:**

- `SubmissionRepository.findByUserId(userId, Pageable): Slice<SubmissionEntity>`: `Slice` не делает лишний `COUNT(*)`, ему достаточно знать, есть ли следующая страница. Порядок `created_at DESC, id DESC`.
- `SubmissionService.listPageForUser`; название, файл и теги подтягиваются пачкой только для записей страницы.
- Побочная находка: у записей с одинаковым временем создания старый массив выдавал порядок неопределённо, а страницы стабильно. Старый метод переименован в `findByUserIdOrderByCreatedAtDescIdDesc`, порядок теперь единый.
- 16 тестов `TranscriptionListPagingIntegrationTest`: массив как раньше и его поля, страницы (стык, ровно полная последняя, за концом), `size` без `page` и наоборот, одинаковые даты, чужие записи, 400 на неверные параметры, 401 без токена.

**Flutter:**

- `TranscriptionRepository.list(query, {page, size})` теперь возвращает `TranscriptionPage(items, hasNext)`. Заглушка и HTTP-репозиторий режут страницы; для запроса по умолчанию HTTP-репозиторий идёт на gateway с `page/size`, а поиск, фильтры и сортировки пока считает на клиенте по полному массиву (до 2c).
- `TranscriptionListController.loadMore()`: добавляет следующую страницу, не дублирует уже известные записи, не запрашивает дважды подряд, отбрасывает ответ, если список сменился (новый запрос, обновление). Ошибка страницы останавливает автозагрузку, пока пользователь не нажмёт «Couldn't load more. Try again». Смена запроса начинает с первой страницы.
- Обновление (опрос раз в 3 с, переименование) перезапрашивает страницу 0 размером «сколько показано», округлённым вверх до 30 (не больше 500): прокрутка не теряется, прогресс и новые записи подхватываются разом.
- Экран: следующая страница подгружается, когда до конца остаётся 5 строк; под списком спиннер или сообщение об ошибке.

**Проверено:** 121 тест gateway (было 105), 231 тест Flutter (было 204). Вручную на локальном gateway: 65 записей, страницы 30/30/5 с `has_next` true/true/false, `size=0` даёт 400, массив без параметров прежний; в приложении прокрутка до конца дошла до самых старых записей.

**В 2a не сделано:** восстановление позиции прокрутки после перехода на другой экран и обратно (загруженные записи остаются в контроллере, но страница создаётся заново и открывается сверху) и больше 500 загруженных записей (потолок размера обновления: при обновлении список сожмётся до 500, дальше подгружается снова).

### Итерация 2b: что важно знать

**Решения (обсуждены с владельцем):**

- **Прогресс: процент только у распознавания, дальше фаза без процента.** `processing_pct` (0-100) есть, пока идёт распознавание; при диаризации и саммари процента нет, полоса полная, подпись меняется: «41% — transcribing…» → «Diarizing…» → «Summarizing…». Ничего не выдумываем: доля диаризации и саммари во времени неизвестна, поэтому «сквозной» процент с весами был бы придуманным.
- **Число спикеров считается SQL-запросом по `jsonb`** (число различных меток `speaker` в `segments`), без миграции и без новых колонок. Заодно список перестал загружать в память сегменты всех транскриптов (раньше `findBySubmissionIdIn` тянул их целиком при каждом обновлении, а опрос идёт раз в 3 секунды).
- **Сид: готовые записи из макета и одна `failed`.** `pending`/`processing` не сидим: оркестратор при старте подхватывает такие строки и доводит их на заглушке, поэтому они не удержались бы. Эти состояния получаются загрузкой файла.
- **Сид пишется через `ON CONFLICT ... DO UPDATE`** с фиксированными id: его можно дополнять без сброса БД, а сидовые записи возвращаются к тому, что написано в файле (правка сидовой записи вручную откатится при следующем изменении файла). Удалённые из файла строки в существующей БД остаются (нужен `scripts\dev-reset.ps1`).

**gateway:**

- В `GET /transcriptions` (и в массиве, и в страницах) новые необязательные поля: `audio_duration_s` (из `audio_meta.duration_s`, появляется, когда transcriber закончил), `speaker_count` (только если есть транскрипт), `processing_pct`, `processing_phase` (`transcribing`/`diarizing`/`summarizing`). Пустые поля не отдаются вовсе.
- Прогресс берётся из `OrchestratorService.getLiveProgress` (память процесса). После перезапуска gateway у записи `processing` нет ни фазы, ни процента, клиент показывает «Processing…». Статус в ответе остаётся сырым (`summarizing` не превращается в `processing`), фаза из него выводится: `summarizing`.
- `TranscriptListQueries` (новый): один запрос на `id`, название и число спикеров транскриптов страницы. Защита от неожиданного `jsonb` (`null`, скаляр, пустой массив, `SQL NULL`): считает 0, а не падает.
- Побочная находка: **моя заглушка transcriber из итерации 0 отдавала `diarize_progress` в процентах (0-100), а настоящий transcriber отдаёт долю 0.0-1.0.** Исправлено на долю (и тест).
- `R__seed.sql` расширен: пользователь, 6 транскрипций (5 готовых с длительностью, тегами, 3/2/0/3/3 спикерами и сегментами примерного диалога, одна без названия, плюс `failed`), теги с описаниями из макета, связи.

**Flutter:**

- `Transcription.processingPhase` (`ProcessingPhase`), разбор новых полей в `HttpTranscriptionRepository`. Подпись и заполнение полосы в строке зависят от фазы (`Transcribing…` без процента оставляет полосу пустой).
- `formatDuration`: файл короче минуты показывается как «<1 min» (раньше «0 min»).
- Сортировка «Longest» на клиентском запасном пути теперь работает по настоящим длительностям.

**Проверено:** gateway 143 теста (было 121): `TranscriptionListFieldsIntegrationTest` 13, `ProcessingProgressTest` 7, `LocalProfileIntegrationTest` +2 (список из сида, повторное применение сида ничего не меняет). Flutter 242 теста (было 231). Вручную: на свежей БД сид даёт 6 записей с длительностью, спикерами и тегами; загруженный файл проходит `processing` без фазы → `transcribing` 0-81% → `diarizing` → `done` с `audio_duration_s` и `speaker_count`; в приложении «40% — transcribing…» и пилюли спикеров.

**Что заметно при сравнении с макетом (не ошибка 2b, но пригодится в итерации 4):** цвета тегов в режиме `local` получаются по хэшу имени (так решено в `api-gaps.md`) и отличаются от цветов макета: `meeting` розовый, а не синий, `quarterly` оранжевый, а не зелёный. Вопрос про хранение цвета (`docs/design.md` хранит его в БД, `api-gaps.md` считает на клиенте) остаётся открытым.

### Итерация 2c: что важно знать

**Решения (обсуждены с владельцем):**

- **Один динамический SQL-запрос для всех случаев** (пустой список, любые фильтры, любая сортировка): производные методы Spring не умеют соединять таблицы, а названия, длительности и теги лежат в соседних. Метод `findByUserId(Pageable)` из 2a удалён, порядок и границы страниц гарантированно одинаковы во всех вариантах.
- **Поиск идёт по отображаемому названию**: название транскрипта, а при его отсутствии имя файла. Запись с названием по имени исходного файла не находится (список этого имени не показывает).
- **Несколько тегов означают «любой из»**, несколько статусов тоже; между группами (статус, теги, поиск) действует «и».
- **Минимальный `GET /tags`** (`[{id, label}]`, все теги пользователя в порядке создания, включая неиспользуемые) для меню фильтра: раньше клиент собирал теги, выкачивая весь список записей, что сводило пагинацию на нет. Итерация 4 расширит эндпоинт (описание, записи, создание, правка, удаление).

**gateway:**

- `SubmissionListQuery`: собирает запрос из фиксированных фрагментов; всё, что приходит от клиента (пользователь, текст поиска, статусы, теги, страница, размер), передаётся как параметры, колонка сортировки берётся из закрытого списка, в текст SQL от клиента не попадает ничего. Запрос возвращает только `id` страницы (`LIMIT size+1` даёт `has_next`), остальное собирает прежний код пачками с сохранением порядка.
- Параметры `GET /transcriptions` (в обоих видах ответа): `q`, `status` (`pending`/`processing`/`done`/`failed`; `processing` включает `summarizing`), `tag`, `sort`. Списки передаются повторением параметра; запятая не разделитель (её читают из запроса напрямую, иначе Spring разрезал бы `q3,planning` на два тега). Неизвестный `status` или `sort` даёт 400.
- Поиск: `ILIKE ... ESCAPE`, `%`, `_` и `\` в тексте пользователя ищутся как обычные символы; пробельный `q` не фильтрует; регистр (в том числе кириллица) сворачивает база.
- Сортировки: `longest` по убыванию длительности, неизвестные длительности в конце; `name` по `lower(отображаемое название)`; при равенстве всегда по дате и `id` (порядок стабилен).
- **Схема БД не менялась, миграций нет**: для прода изменение чисто кодовое.
- Сид: у тегов заданы `created_at` (порядок библиотеки как в макете).

**Flutter:**

- `HttpTranscriptionRepository.list` отправляет `page`, `size` и только то, что сужает или упорядочивает список (`q` обрезанный, `status` по именам enum в фиксированном порядке, `tag` отсортированные и повторяющиеся, `sort` кроме `newest`); ответ показывается как пришёл, локальной фильтрации и сортировки больше нет. `tags()` читает `GET /tags`.
- Поиск: запрос уходит не на каждую букву, а через 250 мс после паузы (`searchDebounce`); поле показывает текст сразу; выбор фильтра или сортировки отправляется немедленно и заменяет ожидающий запрос; после `dispose` ничего не уходит.
- В меню Filter теперь пункт «Failed» (статус добавлен в итерации 1) и теги библиотеки.

**Проверено:** gateway 185 тестов (было 143): `TranscriptionListFilterIntegrationTest` 33 (поиск: регистр, кириллица, имя файла, подстановочные символы, кавычки; статусы; теги: любой из, точное совпадение, запятая, чужие; сортировки со связями; комбинации со страницами; оба вида ответа; `GET /tags`), `SubmissionListQueryTest` 9. Flutter 257 тестов (было 242): запрос, дебаунс. Вручную: `q`, `status`, `tag`, `sort` и их сочетания на живом gateway; в приложении меню Filter показывает теги библиотеки, комбинация «Failed + meeting» даёт пустой список.

**Ограничения и что дальше:**

- Индекса под `ILIKE '%…%'` нет: на сотнях записей не нужен, на десятках тысяч появится (аддитивный индекс, отдельно).
- Порядок сортировки по названию зависит от настройки сортировки базы (`en_US.utf8` локально, на проде скорее всего то же, не проверялось): знаки препинания она не учитывает.
- Итерация 2 (список) закончена.

### Итерация 3: что важно знать

**Решения (обсуждены с владельцем):**

- **Новый `GET /transcriptions/{id}`** вместо `GET /jobs/{id}`: у старого нет проверки владельца, а формат заточен под старый клиент. Старый эндпоинт не тронут.
- **Саммари показывается ровно так, как записано: это Markdown.** Gemini отдаёт один текстовый блок (заголовки `**…**`, списки `*`), и выделять из него «ключевые пункты» и «action items» отдельными полями сервер не пытается. На клиенте `Summary` из трёх частей заменена строкой; рисует её пакет `flutter_markdown_plus`.
- **Кнопки `.txt` и Copy работают обе**, текст берут из существующего `GET /transcript?jobId=` (формат `[00:00:00.000 --> 00:00:30.000] [SPEAKER_00] текст`).
- **Сид: саммари как в макете для всех готовых записей, кроме голосовой заметки** (id 4: на ней видно Overview без саммари). У записи 2 списки написаны через «•», а не Markdown: другая форма, в которой модель тоже отвечает.

**gateway:**

- `GET /transcriptions/{id}` (`SubmissionService.getDetail`): `job_id`, `file_name`, `title` (без названия имя файла), `file_size_bytes`, `created_at`, `status`, `audio_duration_s`, `language`, `word_count` (считается при чтении по тексту сегментов), `tags`, `summary` (Markdown), `segments` (`start`, `end`, `text`, `speaker`; без диаризации `speaker` нет). Пустые поля из JSON выпадают, как и везде. **404** для несуществующей, чужой записи и неверного UUID (id чужих записей не подобрать); без токена 401. У записи без транскрипта (ещё в работе) `segments` пусты.
- `PATCH /jobs/{id}/title`: название обрезается по краям, длиннее 200 символов (столько в колонке `VARCHAR(200)`) даёт 400, а не ошибку БД; пустое возвращает имя файла.
- Схема БД не менялась, миграций нет.

**Flutter:**

- `HttpTranscriptionRepository.get` (404 → `null`, запись не в статусе `done` тоже `null`), `rename` (`PATCH`, ошибка сервера показывает его сообщение), `transcriptText`, `speakers()` пока возвращает пустой список (библиотека спикеров подключается в итерации 5, без него страница не открылась бы).
- `Segment.speakerSlot` может быть `null`: метка `SPEAKER_NN` превращается в слот `NN+1`, без диаризации слота нет. Такой транскрипт рисуется одним блоком с серой линией и без заголовка спикера; ряд «Speakers:» скрыт, число спикеров считается по разным меткам.
- Кнопки шапки: `.txt` сохраняет файл через `TextSaver` (браузер: Blob + ссылка, `package:web`; в тестах подменяется), имя файла из названия без символов, которые не любит файловая система; Copy кладёт текст в буфер. После нажатия подпись на 1,6 с меняется на «Saved»/«Copied», при ошибке на «Failed».
- Markdown: одиночный перенос строки становится жёстким (иначе строки «• …» слипались бы в абзац); списки не трогаются. Оформление в палитре приложения. Ссылки пока не кликабельны.
- В моке саммари переписано в Markdown, как у Gemini.

**Проверено:** gateway 192 теста (было 185): `TranscriptionDetailIntegrationTest` 7 (поля, без саммари и названия, запись в работе, чужая/несуществующая/кривой id, без токена, правила названия). Flutter 279 тестов (было 257): разбор ответа, переименование, текст, Markdown, кнопки, транскрипт без диаризации. Вручную на живом gateway: обе вкладки, записи с Markdown и с «•», запись без диаризации и без саммари, переименование, 404.

**Ограничения и что дальше:**

- Цвета тегов считает сервер по названию и они не как в макете (решено в итерации 4).
- Спикеры показываются как «Speaker N», назначать имена нельзя до итераций 5–6; подсказки AI до 8.
- Размер тела ответа: длинные записи отдаются целиком одним запросом (часовая запись порядка сотен КБ); постраничная выдача сегментов не нужна, пока это не станет заметно.
- Итерация 3 закончена.

### Итерация 4: что важно знать

**Решения (обсуждены с владельцем):**

- **Цвет тега считает сервер по названию, ничего не хранится.** Схема БД не меняется. Цвет не ограничен десятью оттенками палитры: тон берётся по всему кругу (`hue` 0–359), насыщенность и яркость из трёх значений, плюс подтемнение жёлто-зелёных, чтобы белый текст на пилюле читался (контраст не ниже 3,4). Цвета в `local` отличаются от макета, это принято. Цена решения: **переименование тега меняет его цвет**. Формула зафиксирована тестом на конкретное значение (`meeting` → `#8F13AE`): менять её нельзя, не перекрасив все теги.
- **Привязка тегов: новые эндпоинты рядом со старыми**, как в итерациях 2–3. Старые `POST /jobs/{id}/tags {tag}` и `DELETE /jobs/{id}/tags/{имя}` не тронуты (их использует старый клиент).
- **Имя тега:** 1–32 символа, буквы любых языков, цифры, `-` и `_`, без пробелов; хранится в нижнем регистре, по краям обрезается. Уникальность без учёта регистра достигается тем, что всё хранится в нижнем регистре (уникальный индекс `(user_id, name)` уже был). Старый эндпоинт по-прежнему принимает только ASCII: он не менялся.
- **Использование тега на карточке:** `transcription_count` и названия двух последних записей (`sample_titles`); ответ не растёт с числом записей.

**gateway:**

- `GET /tags` теперь возвращает объект `{tags: [...], tagged_transcriptions: N}`. Тег: `id`, `label`, `color`, `description` (нет, если пусто), `transcription_count`, `sample_titles`. `tagged_transcriptions` считает записи с любым тегом один раз (для подзаголовка «used in N files»). Форму из 2c (`[{id, label}]`) использовал только новый клиент.
- `POST /tags {label, description?}` → 201 `{id, label, color}`; `PUT /tags/{id} {label?, description?}` (что не прислано, остаётся; `description: ""` очищает); `DELETE /tags/{id}` → `{affected_transcriptions}` (связи с записями уходят каскадом, сами записи не затрагиваются). Занятое имя даёт 409, плохое имя или описание длиннее 500 символов 400, чужой, несуществующий тег и не-UUID 404.
- `POST /transcriptions/{id}/tags {tag_id}` или `{label, description?}` (новый тег создаётся в библиотеке, существующий переиспользуется; повторная привязка ничего не меняет) → `{id, label, color}`; `DELETE /transcriptions/{id}/tags/{tagId}` → 204, снимает тег только с этой записи, отсутствие связи не ошибка. Чужая запись или тег 404; запись без транскрипта 409.
- **В новых формах ответа тег описан объектом `{id, label, color}`:** в постраничном списке (`GET /transcriptions?page=`) и в `GET /transcriptions/{id}`. **Обычный массив без `page`/`size` по-прежнему отдаёт имена строками**: его читает старый клиент.
- Запросы библиотеки (`TagLibraryQueries`): два запроса на всю библиотеку (счётчики и последние названия окном `row_number()`), а не по запросу на тег.
- Схема БД не менялась, миграций нет.

**Flutter:**

- `HttpTranscriptionRepository`: `tags()`, `tagLibrary()` (теперь возвращает `TagLibrary{entries, taggedTranscriptions}`), `createTag`, `updateTag`, `deleteTag`, `addTag`, `removeTag`. Экраны знают тег по названию, сервер по id, поэтому перед изменением, удалением и снятием тега репозиторий один раз спрашивает `GET /tags` и находит id по названию (название уникально у пользователя). Цена: лишний маленький запрос на действие.
- Цвета берутся с сервера (`#RRGGBB`); неверный или отсутствующий цвет становится серым, а не ломает список. Клиентская функция `colorForLabel` удалена.
- `TagEntry` получил `count` отдельно от названий: с сервера приходят только два последних названия, а число файлов настоящее (в моке названий столько же, сколько записей, как раньше).

**Проверено:** gateway 221 тест (было 192): `TagLibraryIntegrationTest` 24 (создание, правила имени, дубли без учёта регистра, библиотека со счётчиками и названиями, правка, удаление, привязка и снятие, чужие данные, форма в списке и в детали), `TagColorsTest` 5 (детерминизм, регистр, формат, зафиксированное значение, разброс, контраст). Flutter 288 тестов (было 279): 12 новых на запросы и разбор, 3 устаревших (цвет по хэшу, заглушки) убраны. Вручную на живом gateway: полный цикл создание → привязка → дубль (409) → переименование → снятие → удаление; кириллическое имя; страница Tags и список в браузере (цвета, счётчики, названия, «used in 4 files»).

**Ограничения и что дальше:**

- **Ошибки сервера пока не показываются пользователю**: если `POST /tags` вернёт 409/400 (клиент проверяет занятое имя заранее, но не формат), действие молча не удаётся, в консоли исключение. Единого показа ошибок (плашка) для экранов ещё нет; его стоит сделать до слияния в `master` (пункт итерации 9).
- Название тега с пробелом («weekly sync») клиент пропустит, сервер откажет 400: то же, что выше.
- Тег, снятый в другой вкладке между запросами, остаётся «снятым» без ошибки (идемпотентность).
- Итерация 4 закончена. Следующая — 5 (библиотека спикеров).
